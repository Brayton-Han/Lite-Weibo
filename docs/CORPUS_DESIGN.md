## 1. 总体构成

按**信息需求**分层，不按主题分。总计 **3000 条**。

| 层 | enum | 条数 | 簇数 | 检索意图 | 来源 | 是否进生成层 |
|---|---|---|---|---|---|---|
| 经验类 | `experience` | 900 | 12 × 75 | 求答案 | 合成 | ✅ 唯一进生成层的一层 |
| 共鸣类 | `resonance` | 1200 | 12 × 100 | 求同类 | 合成 | ❌ 转语义搜索 |
| 噪声 | `noise` | 900 | 8 类不计簇 | —— | **LWC**（CC BY-NC-SA，见 §5） | ❌ 默认不相关 |

**层的比例依据**：真实社交平台上承载可回答信息需求的内容约占三成，这是 Day 13 意图路由
和 Day 14 三路拒答的设计前提。比例失真，整个生成层的收窄论证就失去依据。

## 2. 核心约束：同义表达族

**这是整份设计的命门。** 每个靶区簇内必须切分成若干「同义表达族」——
族内的帖子讲同一件事，但**尽量不共享实词**。

- 词面检索（`LIKE` / tsvector）只能召回与 query 共享 term 的帖子
- 向量检索召回的是语义邻近的帖子
- **只有当同一族内存在词面零重叠的样本时，两者的差距才测得出来**

族也是 Day 8 构造 pooling 候选池的单位，且让 Day 3 验收标准
（「每簇能找出至少 3 组词面零重叠但语义相同的帖子对」）可以机械校验。

每簇 4 个族，经验类每族 ≈19 条，共鸣类每族 ≈25 条。

## 5. 噪声层 · 900 条

干扰项池。唯一作用是把语料撑到 3000 条，让 top-10 只覆盖 0.3% 的库，使 Recall@10 不虚高。

**内容构成**：打卡签到 / 天气 / 饮食日常 / 追剧与游戏 / 抽奖转发 / 节日祝福 /
自拍配文 / 无主题碎碎念。

### ⚠️ 硬约束一：必须主题中立

噪声层**不得包含情绪表达类内容**，否则会与共鸣类 12 簇语义重叠，后果是：

1. 噪声层混入与共鸣类 query 真正相关的帖子
2. 它们不在 ground truth 里 → 被判为不相关 → **假阴性**
3. Recall 被系统性压低，且**压得不均匀**——向量检索更容易召回这些语义相关的帖子，
   于是**它被罚得更重**

净效果是评测偏向词面检索、打压向量检索，与本项目要证明的方向相反。
且这种偏差不会报错，只会让数字悄悄变难看。

### ⚠️ 硬约束二：「默认不相关」≠「不参与标注」

IR 中未判定文档按不相关处理，但**该假设成立的前提是 pooling 覆盖了所有待测系统的 top-k**。
因此：噪声层不进入 Day 8 的 query 构造，但**只要它出现在候选池里，就必须照常做 0/1/2 判定**。
不能因为「它是噪声层」而跳过。

### 数据来源与许可（核查完毕 · 2026-09-18）

共核查 4 个候选。**结论：采用 Leiden Weibo Corpus (LWC)。**

#### 已知代价（接受）

1. **2012 年数据**。对噪声层影响有限：噪声层的职责是撑规模 + 提供真实词汇/句式噪声，

2. **取数成本**：978 MB 下载 + 解 SQL dump + 从 parsed 格式还原纯文本，仅为提取 900 条。
   约一小时体力活，无技术难度。

#### 抽取要求

- [ ] 从 `parsed_messages.sql` 还原纯文本（剥离分词标记与词性标注）
- [ ] 按 **30–200 字** 过滤（口径见 §5.5）
- [ ] ⚠️ **主题中立过滤**（见上方「硬约束一」）：剔除与 `R01`–`R12` 共鸣类簇语义重叠的内容。
      900 条量级可人工扫完，务必扫一遍
- [ ] 抽满 900 条，写入 manifest（`layer: "noise"`, `cluster: null`）

#### 实际执行结果（2026-09-18）

扫描 5,103,557 行 → 通过 366,xxx 条 → 蓄水池去重后候选 3,490 条 → 随机抽 900 条。

过滤链：纯转发无正文（7.5%）→ 长度不在 30–200 → 主题中立关键词过滤 → 近重复去重
→ 字符 bigram 近重复去重。

**⚠️ 未做 LLM 语义复筛——这是有意的取舍，且它有一个承重依赖。**

人工抽检 40 条实测：**明显撞车 7 条（17.5%），含轻度共 12 条（30%）**，
折算到 900 条约为 **150–270 条**。关键词过滤挡不住语义近似，漏网的典型是
鸡汤体与抒情文（「以后同学聚会再也不去了…」「突然有些怀念绍兴的白墙黑瓦」），
以及粤语/港式表达绕过繁体检测的房产、育儿内容。

**为什么接受**：Day 8 的 pooling 从各检索系统各取 top-20 汇总后统一标注，
真正与 query 相关的噪声帖会在那一步被标成相关，不构成假阴性。
而且**候选池的大小由 top-k 决定，不由语料污染度决定**——污染只改变池子里
出现的是哪些文档，不增加要标注的条数。额外成本接近于零。

> 🔗 **承重依赖**：上述论证完全依赖「pooling 覆盖了所有待测系统」。
> 若 Day 8 退化为只标注单一系统的 top-20，这 150–270 条会变成真实的评测偏差，
> **且偏差方向是打压向量检索**——因为向量更容易召回这些语义相关的噪声帖。
> 见 `docs/EVAL.md` §2。

#### Fallback（若 LWC 抽取后不足 900 条或质量不达标）

改为合成，并在 `EVAL.md` 显式记录：「噪声层为合成数据，存在分布偏移风险；
真实社交语料的噪声在用词随机性和句式破碎度上高于合成结果，本评测的绝对数字可能偏乐观，
但各检索方案之间的**相对**对比不受影响。」

## 5.5 长度口径（2026-09-23 修订）

| 环节 | 口径 | 理由 |
|---|---|---|
| 生成 prompt | 60–200 字 | 瞄高。实测 p50 落在 68，够长才造得出同义表达族 |
| `validate.py` | **30–200 字** | 容纳模型自然方差。实测 47–112，卡 60 会有 17% 误判失败 |
| LWC 噪声抽取 | **≥30 字** | 与校验同口径 |
| 噪声抽样 | **按靶区实际分布分层匹配** | 见下 |

### 上限 200 的理由（不变）

保住 Day 5「一条 post 一个向量」的设计。长文本压成单向量会严重稀释语义，
要救就得引入 chunk 表，那是表结构变更。

### 下限为什么从 60 降到 30

原先的 60 没有论证，只有一句「低于 60 字信息量不足」的感觉。实测 LWC 真实长度分布：

| 字数 | 占比 |
|---|---|
| 0–19 | 37.7% |
| 20–39 | 24.0% |
| 40–59 | 11.7% |
| ≥60 | **19.1%** |

**≥60 只覆盖真实微博最长的五分之一。** 更关键的是方向：文档越长 term 越多、
与 query 撞上的概率越高，**长文档天然利好词面检索**——而本项目的核心论点恰恰是
「短社交文本上向量赢词面」。60 字下限是在给对照组送分。

保留 30 而非完全取消，是因为两个真实约束：过短的帖子 embedding 信号弱、
Day 8 相关性标注也变模糊；且靶区需要一定长度才造得出「用完全不同的词说同一件事」的同义族。

### ⚠️ 抽样要做分层匹配，仅对齐上下界不够

两层若长度**实际分布**不一致（靶区 p50 68 vs 噪声 p50 40），
「长度」就成了与语料层相关的特征，任何偏好长文档的检索方法都会虚高。
对齐边界解决不了，必须对齐分布：

```bash
python sample_noise.py --match-lengths ../../corpus/manifest.jsonl
```

桶宽 10 字分层抽样。某长度段供给不足会打印警告而非静默吞掉。

## 6. 生成 manifest 格式（Step 2 的输出 / Step 4 的输入）

`corpus/manifest.jsonl`，每行一条：

```json
{
  "gen_id": "E01-0007",
  "layer": "experience",
  "cluster": "E01",
  "cluster_name": "租房避坑",
  "family": "中介费议价",
  "style": "吐槽",
  "content": "中介张口就要一个月房租的服务费，这合理吗……"
}
```

| 字段 | 说明 |
|---|---|
| `gen_id` | 生成侧主键，`{cluster}-{序号}`。导入时换成 DB 分配的 `post_id` |
| `layer` | `experience` / `resonance` / `noise` |
| `cluster` | 噪声层为 `null` |
| `family` | 同义表达族名，Day 8 构造 pooling 候选池时用 |
| `style` | `吐槽` / `提问` / `科普` / `转发评论` / `中英混杂` / `日记`，保证风格多样性 |
| `content` | 生成瞄准 **60–200 字**，校验放宽到 **30–200**（见 §5.5） |

导入器负责把 `gen_id → post_id` 的映射落进 `corpus_meta(post_id, layer, cluster, family)`。
原有的 57 条真实帖子保持 untagged，eval 时单独排除。

### ⚠️ `R04-1` 的 13 条是人工补写的

全量批次中 `R04-1`（原生家庭催婚 · 相亲安排族）生成退化：只产出 12 条而非 25 条，
其中 4 条是 8–27 字的残句。该族**未触发 `max_tokens`**，是模型自身的质量问题。

重跑时 API 额度耗尽，遂保留 8 条合格的、剔除 4 条残句、人工补写 17 条。
这 17 条通过了与合成语料相同的校验（长度 30–200、族内零重叠 297/300、无近重复）。

**代价：这 13 条不可由脚本复现。** 若需要完整的「重跑一遍结果一样」，
执行下列命令覆盖该族即可（约 $0.03）：

```bash
tools/corpus_gen/.venv/bin/python tools/corpus_gen/generate.py run \
    --only R04-1 --model claude-sonnet-5 \
    --style-samples corpus/style_samples.txt --interval 120
```

### 语感锚点

生成时传入了 30 条**真实微博**作为语言风格参考（`--style-samples`），
