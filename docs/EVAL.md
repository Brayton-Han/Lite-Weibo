## 如何复现

```bash
# backend 容器占着 8080，所以加 --server.port=0；向量路首次运行需要 VOYAGE_API_KEY，之后走缓存
cd backend
EVAL_RUN=true VOYAGE_API_KEY=... ./mvnw spring-boot:run \
  -Dspring-boot.run.profiles=tools -Dspring-boot.run.arguments=--server.port=0
```

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `EVAL_SPLIT` | `train` | `train` / `test` / `all`；**test 只在 Day 18 跑一次** |
| `EVAL_STRATEGIES` | `like,tsrank,vector` | 逗号分隔；另可选 `rrf`、`rrf-serial`（两路串行，只用来量并行收益） |
| `EVAL_K` | `10` | 截断深度 |
| `EVAL_EF_SEARCH` | `embedding.search.ef-search`（100） | 向量路的 `hnsw.ef_search` |
| `EVAL_TRGM_THRESHOLD` | `search.trgm.threshold`（0.05） | tsrank 中文路的 `pg_trgm.word_similarity_threshold`（`<%` 命中下限）；pg 默认 0.6 对中文几乎不返回结果 |
| `EVAL_RRF_N` / `EVAL_RRF_K` / `EVAL_RRF_W` | `20` / `10` / `10` | rrf 策略每路召回条数、平滑常数、向量一路权重（词面为 1）；默认值为 Day 11 选定配置 |
| `EVAL_LATENCY_REPEAT` | `1` | 每条 query 计时次数，取中位数；量延迟时调大（Day 11 用 21） |

扫参：`EVAL_EF_SEARCH` / `EVAL_RRF_N` / `EVAL_RRF_K` / `EVAL_RRF_W` 可写成逗号分隔的多个值，vector 按 ef_search、rrf 按四者的笛卡尔积展开，
策略名带上参数（如 `rrf-k10-n20-ef100-w10`），结果写到 `eval/results/sweep_{split}_{时间戳}/`，汇总为每个配置一行。

输出：`eval/results/{strategy}_{split}_{时间戳}.tsv`（逐 query 明细，`ranked` 列为 `post_id:grade`，池外帖子记 `?`）
与 `eval/results/summary_{split}_{时间戳}.md`。query 向量缓存在 `eval/work/query_vectors.jsonl`（不进 git）。

## 口径

- **只在 3000 条语料帖中排名**：库里另有 157 条没有 `corpus_meta` 的真实帖子（Day 3 时为 57 条，之后开发测试又发了一些），
  它们从未被标注，从结果中剔除；剔除后不足 k 条就加深重取，保证仍是该策略真正的 top-k
- 指标为 35 条可答 query 的宏平均；分级 nDCG 用 0/1/2，其余三项把 grade > 0 视为相关
- 5 条无答案 query 不进均值，单独报「返回空结果」
- **judged@k**：返回结果里有判定的比例。三条基线都是 Day 8 候选池的来源（池深 20），应为 100%；
  之后的策略若明显低于 100%，未判定的帖子按不相关计分，指标会低估它——要先补标再下结论
- 延迟：每个策略先空跑一遍预热，再计时；只计一次深度为 k 的调用（与线上一致），剔除非语料帖所需的加深重取不计入。
  单进程串行、本机 Docker PostgreSQL，p50 / p95 为最近秩分位数，样本只有 40 个
- 向量路延迟**不含** embedding API 调用

### 读数

1. **`like` 的问题首先是召回而不是排序。** 35 条可答 query 里 27 条一条结果都没有：synonym 10/10、mixed 5/5、共鸣 12/12 全部为空——
   `'%整句 query%'` 要求帖子逐字包含整句。只有 keyword 类能命中（8/8 非空，MRR 1.000），但每条只命中约 2 帖，Recall@10 仅 0.137。
2. **`like` → `tsrank` nDCG 从 0.082 到 0.257（×3.1），但这不是「排序」带来的。** `tsrank` 同时改了两件事：
   匹配条件从「逐字包含整句」放宽成 trigram 模糊匹配，排序从时间改成相关性。提升几乎全部来自前者——
   在 `like` 唯一有结果的 keyword 类上，只换排序的效果是 0.357 → 0.361，基本为零；其余类型是「从没结果到有结果」。
   Day 10 的面试钩子「传统搜索没做好」仍然成立，但要说成**召回条件太死**，不能说成「加个相关性排序 nDCG 就翻三倍」。
3. **向量在每个分组的 nDCG / Recall 上都领先**，差距最大的是 synonym（5.2×），最小的是 keyword（1.8×）。
   共鸣层 MRR 1.000：12 条 query 的第 1 名全部相关。按 query 配对的 bootstrap 95% 置信区间（vector − tsrank 的 nDCG@10）：
   keyword +0.27 [0.04, 0.48]、synonym +0.66 [0.57, 0.75]、mixed +0.41 [0.19, 0.70]、共鸣 +0.58 [0.47, 0.69]，都不跨 0——
   **方向可信，幅度见下方「效度局限」**。
4. **「词面在 keyword 的第一条上占优」只是迹象，不是结论。** keyword 类 MRR：like 1.000 > tsrank 0.875 > vector 0.826，
   但整段差距只来自两条 query：q001「考核期」（向量第 1 个相关结果排第 2）和 q002「脱产复习」（排第 9，nDCG 0.077 vs like 0.335）。
   like − vector 的 MRR 配对 bootstrap 95% 置信区间为 [0.00, 0.41]（n = 8），**统计上不显著**。
   方向与 roadmap 预期的「原词精确匹配上向量会输」一致，值得在 Day 11 盯住这两条，但不能当作 RRF 的依据。
5. **与 roadmap 预期不符：分裂按 query 类型出现，而不是按语料层。** roadmap 预期词面在共鸣层归零、在经验层能打；
   实测 `tsrank` 两层 nDCG 几乎相同（0.255 / 0.259），向量对它的领先在两层也相近（3.3× / 2.8×）。归零的只有 `like`，而它在经验层的 synonym / mixed 上同样归零。
   向量对词面的领先在 keyword 上最小、在 synonym 上最大，但**没有哪一个分组是词面赢的**（见第 3、4 条）。
   **对 Day 11 的含义**：Day 9 的数据**不支持**「两者各有主场，所以要融合」这个论证——它在本评测集上没有显著证据。
   RRF 要么在 Day 11 用数字证明自己（至少不拖累 synonym / 共鸣，并补回 q001 / q002 这类 query），要么就如实写「融合没有带来收益」。
   注意 keyword 只有 8 条、共鸣 12 条，单条 query 就能让分组均值动 0.1 左右。
6. **两条有排序的基线都没有拒答能力**：`tsrank` / `vector` 无阈值，无答案 query 也返回满 10 条。`like` 的 5/5 空结果不是能力，是它对非 keyword query 的通病。
   拒答阈值留到 Day 14。
7. **延迟**：`tsrank` 全表算 `word_similarity`，p95 28 ms，是另两路的十几倍，Day 10 改为 `%` 操作符走 GIN 索引。
   向量 p95 2.1 ms 是修过 plan cache 问题之后的数字，见下。

### 效度局限：相关集基本等于种子帖的同义表达族

这是本评测集最大的局限，所有绝对数值都要带着它读。

| 数据（train，35 条可答 query） | 结果 |
|---|---|
| 相关集中属于种子帖同义表达族的比例 | 平均 **85%** |
| vector top-10 中来自种子族的帖子 | 249 / 350（**71%**），其中 232 条判为相关 |
| vector 命中的相关帖中来自族外的 | 48 / 280 |
| tsrank top-10 中来自种子族的帖子 | 58 / 350；259 条来自其他簇且不相关 |

- **成因**：族是 Day 3 由 LLM 按「讲同一件事、尽量不共享实词」批量合成的（CORPUS_DESIGN §2），族内语义高度同质、族间边界清晰；
  Day 8 又以族为 pooling 单位、由 Claude 按语义判定相关性。于是「相关」在很大程度上等于「同族」，
  评测实际在问「能不能找回一个预先造好的语义簇」——这恰好是 embedding 最擅长的形态。
- **可信的**：策略之间的**排序与方向**（vector ≫ tsrank > like），置信区间都不跨 0。
- **不可外推的**：nDCG 0.766、「领先 3 倍」这类**绝对值与幅度**。真实社交语料没有这么干净的语义分簇，
  换到真实数据上向量的绝对分数大概率明显更低，与词面的差距也可能收窄。简历与面试中引用数字时必须连同这一条一起说。
- **已排除的担心**：
  - 不是 known-item 检索：vector 把种子帖本身排进 top-10 的有 26 / 35 条，但剔除种子帖后 MRR 仍为 0.930（tsrank 0.590、like 0.114），
    说明 Day 8「query 不得使用种子帖独有细节」的约束起了作用；
  - 不是池外漏标：三路 judged@10 均 ≥ 99.8%。
- **缓解方向**（未做）：报一份只计族外相关帖的指标；或补一小批不经合成、直接从真实语料出发的 query 做外部效度检查。

### 顺带发现：向量检索被 generic plan 拖成全表扫描（已修）

第一次跑向量路时 p50 = 283 ms，而 psql 里同一条 SQL 约 1 ms。原因：

- 同一条连接上执行满 5 次后 pgjdbc 改用服务端预编译语句，PostgreSQL 随即改用 **generic plan**；
- generic plan 下 `?::vector` 不再是常量，**每一行都把 12 KB 的向量文本重新解析一遍**（3,156 行 ≈ 275 ms），
  且 LIMIT 未知，规划器放弃 HNSW 改走全表扫描——延迟随语料线性增长。psql 里用 `plan_cache_mode = force_generic_plan` 复现为 275 ms。

**线上语义搜索端点走的是同一条 SQL，同样受影响。** 修法：`searchNearest` 的事务里加 `SET LOCAL plan_cache_mode = force_custom_plan`，
修后 p50 1.9 ms，指标不变。

评测侧也有一个同类陷阱：最初为剔除非语料帖一次多取 157 条，内层 LIMIT 变成 501，规划器就从 HNSW 换成精确全表扫描，
测的不再是线上路径。现在改为先按 k 取、不够再加深重取；延迟只计深度为 k 的那一次调用
（trgm 一路 40 条里有 32 条的 top-10 混有非语料帖要重取，计进去会把延迟虚抬一倍以上）。

## Day 10 · 中文 trgm 阈值扫参（train，k = 10，仅 tsrank）

### 读数

1. **定 0.05。** 指标随阈值单调下降，不存在「调严反而更准」的区间——阈值只截断、不改变留下的帖子的相对顺序，
   被截掉的低分帖里也有相关帖。所以选「不损失任何指标的最大阈值」。
2. **0.05 实际等于「至少共享一个 trigram」。** 这批 query 最多 16 个 trigram，最小非零分 ≥ 1/16 = 0.0625，因此 0.05 与 0 结果完全相同。
   超过约 20 个 trigram 的长 query 下，0.05 才会开始截掉只共享一个 trigram 的帖子。
   候选集中位数 48 / 3157（约 1.5%），最多 468——索引仍有剪枝空间。
3. **先掉的是 synonym 与共鸣层，keyword 最耐截断。** 词面重叠本来就少的 query，相关帖的分数集中在 0.1–0.2，
   阈值一上来先被截掉；keyword 的相关帖往往原样含 query，到 0.25 才开始掉。
4. **0 与 Day 9 全表算分的指标完全一致（nDCG@10 0.257），但行为不同：** 走 GIN 索引时只会找到至少共享一个 trigram 的帖子，
   于是 5 条无答案 query 里有 2 条返回空，Day 9 全表算分则一律凑满 10 条（剩下的都是 0 分帖）。延迟 p50 27.0 → 1.6 ms。
   执行计划见下方「执行计划」一节：这个 1.6 ms 是 generic plan 下的，custom plan 当时有 16 / 40 条 query 会退化成 seq scan（已修）。
5. 3000 条语料下各阈值的延迟差（0.5–1.7 ms）可以忽略，阈值的取舍在这个规模上只看质量。

## Day 10 · 词面路升级：tsrank vs like（train，k = 10）

运行：`eval/results/summary_train_20261016-211652.md`（`EVAL_STRATEGIES=like,tsrank`，trgm 阈值 0.05）。
like 的逐 query 结果与 Day 9 逐字节一致，基线可复现。train 40 条 query 全部含汉字，**下面只反映中文路**；英文路的 `ts_rank_cd` 改动在本评测集上没有样本。

| 策略 | Recall@10 | P@10 | MRR | nDCG@10 | p50 ms | p95 ms | 可答 query 零结果 |
|---|---|---|---|---|---|---|---|
| like（LIKE + 时间排序） | 0.031 | 0.049 | 0.229 | 0.082 | 0.9 | 1.3 | 27 / 35 |
| tsrank（trgm 相似度排序） | 0.104 | 0.249 | 0.675 | 0.257 | 1.7 | 3.6 | 0 / 35 |

按 query 配对的 bootstrap 95% 置信区间（tsrank − like，10,000 次重采样）：

| 分组 | n | Δ nDCG@10 | Δ MRR |
|---|---|---|---|
| 全部可答 | 35 | +0.176 [+0.102, +0.252] | +0.447 [+0.270, +0.614] |
| **LIKE 有结果**（= keyword 类） | 8 | **+0.004 [−0.172, +0.172]** | **−0.125 [−0.375, 0.000]** |
| **LIKE 零结果** | 27 | +0.227 [+0.154, +0.306] | +0.616 [+0.446, +0.781] |
| 　· synonym | 10 | +0.157 [+0.073, +0.245] | +0.533 [+0.233, +0.833] |
| 　· mixed | 5 | +0.299 [+0.060, +0.538] | +0.600 [+0.200, +1.000] |
| 　· 共鸣层 | 12 | +0.255 [+0.157, +0.367] | +0.692 [+0.475, +0.896] |

### 读数

1. **nDCG@10 0.082 → 0.257（×3.1），但提升几乎全部来自「命中条件」而不是「排序」。**
   `LIKE '%q%'` 要求 query 原样出现，35 条可答 query 里有 27 条一条都找不到；trigram 只要求部分 3 字窗口重合，这 27 条全部有了结果。
   在 LIKE 本来就有结果的 8 条 keyword query 上，把时间排序换成相似度排序，nDCG 只 +0.004（区间跨 0），MRR 反而 −0.125。
   **所以「光是加上相关性排序就提升 3 倍」的说法不成立**，准确的说法是：从精确子串匹配换成模糊匹配 + 相关性排序，
   提升来自后者能召回不含原词的帖子。
2. **短中文 query 下 trigram 分数没有区分度（q005「小电驴」nDCG 0.470 → 0）。**
   3 字 query 只有 4 个 trigram，其中 2 个带词边界填充。原样含「小电驴」的帖子只配上中间那个，得 0.25；
   只在标点后出现「小」（如「，小明…」）的无关帖子配上 `␣␣小`，也是 0.25。48 条帖子并列 0.25，按 id 升序取前 10，
   4 条相关帖（id 4713–5391）全被挤出。「考核期」能拿 0.5 是因为相关帖里它后面紧跟标点，`核期␣` 也配上了——同样是 3 字 keyword，分数取决于前后是不是标点。
   可选的修法（未做，留给 Day 11–12 评估）：并列时按 `content LIKE '%q%'` 或 `similarity()` 二次排序。
3. 延迟 p50 0.9 → 1.7 ms，在 3000 条语料下可忽略；执行计划见下一节。
4. 与 vector（Day 9，nDCG@10 0.766）相比，升级后的词面路仍差 3 倍。Day 11 的 RRF 要回答的是：这一路在哪些 query 上能补向量的短板——
   按上面第 1 条，最有希望的是 keyword 类，而那恰好是 trigram 相对 LIKE 没有改进、短 query 还会退化的地方。

### 执行计划：中文路在 custom plan 下会退化成 seq scan（已修）

`EXPLAIN ANALYZE`，阈值 0.05，用 `PREPARE` 分别在 `plan_cache_mode = force_custom_plan / force_generic_plan` 下看
（pgjdbc 每条连接前 5 次执行是 custom plan，之后改用服务端预编译语句，可能换成 generic plan）：

| SQL | custom plan | generic plan |
|---|---|---|
| 英文 `@@` + `ts_rank_cd`（`the`） | Bitmap Index Scan `idx_post_search`，0.06 ms | 同左，0.05 ms |
| 中文 `<%`，`考核期` | Bitmap Index Scan `idx_posts_content_trgm`，0.2 ms | — |
| 中文 `<%`，`通勤两小时` | **Seq Scan，32.8 ms** | Bitmap Index Scan，2.6 ms |
| 中文翻页（带游标），`通勤两小时` | **Seq Scan，29.5 ms** | Bitmap Index Scan，5.8 ms |

行数估得很准（估 161、实际 147），错的是成本：pg_trgm 的函数都是默认 `COST 1`，规划器把逐行算 `<%` 当成一次简单运算，
seq scan 估 310、bitmap 估 324，于是选了 seq scan。实际对几百字的中文帖子算一次 `word_similarity` 约 10 µs，seq scan 要对 3000 行全算。
train 40 条 query 在 custom plan 下有 **16 条走了 seq scan**，最慢 37.7 ms。
和 Day 9 向量路的问题正好相反：那次是 generic plan 坏、custom plan 好。

修法：`V5__trgm_function_cost.sql` 把 `word_similarity_op`（`<%` 背后的函数）与 `word_similarity` 的 `COST` 调到 100。
修后 custom plan 下 40 条全部走 `idx_posts_content_trgm`，p50 1.13 → 0.99 ms，最慢 37.7 → 8.5 ms，合计 484 → 50 ms。
评测指标与逐 query 排名不变（`eval/results/summary_train_20261016-212040.md`）；评测的 p50 也不变（1.6 ms），
因为预热之后评测量到的本来就是 generic plan——**单看评测延迟发现不了这个问题，要看执行计划。**

注意：对扩展成员函数的 `ALTER FUNCTION` 不会被 pg_dump 导出，从 dump 恢复的库要手动重跑 V5。

## Day 11 · 延迟：混合比单路慢多少

运行：`eval/results/summary_train_20261019-112542.md`（顺序 tsrank → vector → rrf → rrf-serial）与
`summary_train_20261019-112557.md`（倒序），`EVAL_LATENCY_REPEAT=21`：每条 query 计时 21 次取中位数，再对 40 条 query 取分位数。

以前各节的延迟都是每条 query 只测一次，这一节的数字更稳；两种顺序结果基本一致，没有明显的先后偏差。

| vector（单路，N = 10） | 2.1 / 2.1 | 2.8 / 2.4 |
| **rrf（并行）** | **2.4 / 2.4** | **3.7 / 4.4** |

|---|---|---|

### 读数

1. **混合比纯向量慢约 0.3 ms（p50 2.1 → 2.4 ms，+15%），p95 多 1–2 ms。** 并行时耗时 ≈ 较慢的一路 + 约 0.25 ms
   （线程切换与融合）；串行则是两路之和，并行省掉了约 1.7 ms。注意单路是取 10 条、混合每路取 20 条，这个差也算在混合头上了。
2. **尾延迟来自词面路，不是向量路。** 最慢的 q062「又是天亮才睡 一整天都废了」，tsrank 9.3–9.7 ms、vector 1.7–2.1 ms，rrf 跟着到 9.9–10.8 ms。
   这条 query 里「天」「一」之类的常用字让 468 / 3157 条帖子共享至少一个 trigram（Day 10 记录的候选集最大值），

3. **在线上整条链路里这 0.3 ms 可以忽略。** 线上语义搜索每次都要先调一次 embedding API 把 query 向量化（评测走缓存，不含这一步）；
   本环境没有 `VOYAGE_API_KEY`，**这次没有实测**，但一次跨公网的 HTTPS 往返通常在几十到几百毫秒，比检索本身高一到两个数量级。
4. **结论：延迟可以接受，但要和收益一起看。** +0.3 ms 换来的是 nDCG +0.005（不显著，见上一节），收益与成本都很小；
   真正的成本在于多了一条尾延迟随语料增长的链路，以及下面这个未验证的并发问题。

### 未验证：共用 feed 线程池

评测是单线程串行发请求，两路任务总能立刻拿到空闲线程。`feedTaskExecutor` 核心 4 线程、队列 500、满了才 CallerRuns：
如果混合检索上线时继续共用它，发帖扇出高峰时搜索任务会排在几百个扇出任务后面，延迟可能涨到秒级，而这次测不出来。
上线前应改用独立的小线程池（队列短、满了 CallerRuns，相当于退化成串行），并做一次并发压测。

## Day 12 · Voyage rerank：有 / 无 rerank（train，k = 10）

`EVAL_STRATEGIES=rrf,rerank-voyage`，结果 `eval/results/summary_train_20261019-154131.md`。
base 是 Day 11 选定的 rrf（k = 10、N = 20、w = 10、ef_search = 100）；rerank 取 rrf 前 30 条候选，模型 `rerank-3`。
rerank 的延迟含 Voyage API 往返、计时 1 次；两者都不含 query 向量化。

| 策略 | nDCG@10 | MRR | Recall@10 | P@10 | judged@10 | p50 / p95 ms | 成本 / query |
|---|---|---|---|---|---|---|---|
| rrf（无 rerank） | 0.771 | 0.956 | 0.386 | 0.800 | 99.8% | 3.3 / 4.8 | $0 |
| **rerank-voyage** | **0.807** | **1.000** | 0.395 | 0.803 | 92.5% | 123 / 155 | $0.00009（1,741 token） |

按层 × 类型的 nDCG@10：

| 分组 | n | rrf | rerank-voyage |
|---|---|---|---|
| 经验层 | 23 | 0.737 | 0.774 |
| 　· keyword | 8 | 0.657 | 0.713 |
| 　· synonym | 10 | 0.816 | 0.841 |
| 　· mixed | 5 | 0.709 | 0.739 |
| 共鸣层 | 12 | 0.835 | 0.869 |

按 query 配对的 bootstrap 95% 置信区间（rerank-voyage − rrf，35 条可答 query，10,000 次重采样）：

| 指标 | Δ | 95% CI | 赢 / 平 / 输 |
|---|---|---|---|
| nDCG@10 | +0.036 | [+0.005, +0.068] | 23 / 4 / 8 |
| MRR | +0.044 | [+0.000, +0.112] | 2 / 33 / 0 |

### 读数

1. **rerank 显著提升 nDCG@10：+0.036（相对 +4.7%），置信区间下沿在 0 以上，35 条里涨 23 条。** 两层都涨，keyword 类涨得最多（+0.056）——
   Day 11 里 keyword 是 rrf 唯一受益的类型，rerank 没有把这部分吐回去。
2. **MRR 的提升只来自 2 条 query**（第 1 名从不相关变成相关），其余 33 条第 1 名本来就对；区间下沿为 0，单看不显著。
3. **指标偏保守。** rerank 把 rrf 第 11–30 名提进前 10，其中 30 个帖子不在 Day 8 候选池里、按不相关计分（judged@10 92.5%）。
   涨幅最大的 q002（+0.30）、q038（+0.29）各有 2–3 个未判定帖，补标只会让 rerank 的数字更高或不变。
4. **跌幅最大的 4 条**：q043（mixed，−0.20）、q004（keyword，−0.12）、q034（synonym，−0.10）、q006（keyword，−0.10）。
   mixed 类 Recall@10 是唯一下降的分组（0.327 → 0.293），但只有 5 条 query，看不出规律。
5. **代价是延迟：p50 多约 120 ms**，是搜索链路上第二次串行的外部调用（第一次是 query 向量化）。成本可忽略：约 1,700 token / query，按 `rerank-3` $0.05 / 百万 token 不到万分之一美元。

### 决定

**上。** 提升超过路线图定的 3% 门槛且显著，成本可忽略；延迟 +120 ms 对搜索框可以接受。
接入线上时 `RerankStrategy` 开降级（`fallbackOnError = true`，超时 2s），Voyage 不可用时退回 rrf 排序。

## Day 14 · 拒答阈值（train，k = 10）

`EVAL_STRATEGIES=vector,rrf`，结果 `eval/results/{vector,rrf}_train_20261020-155246.tsv`（明细新增 `scores` 列，与 `ranked` 一一对应）。
问题：经验类 query 检索完，**不调模型**就判断"站内没有相关讨论"，用什么判据、阈值多少。

### 判据比较

| 判据 | 无答案 query（n = 5） | 可答 query（n = 35） | 结论 |
|---|---|---|---|
| rrf top-1 | 全部 0.9091 | 0.9091 – 1.0000 | **无信号**：RRF 分数只由名次决定，第一名几乎总是 1/(k+1) 加权和 |
| 向量 top-1 − top-10 | 0.063 – 0.149 | 0.033 – 0.361 | 无答案并不更小，**不可用** |
| 向量 top-1 − top-10 均值 | 0.043 – 0.110 | 0.016 – 0.271 | 同上 |
| **向量 top-1 余弦** | **0.298 – 0.417** | 0.286 – 0.746（35 条里 32 条 ≥ 0.42） | 唯一有区分度的 |

roadmap 曾建议"改用相对判据"来对付分数随 query 漂移（Day 4），实测相对判据在这里反而没有信号：
无答案 query 的检索结果是一堆**同样**不相关的帖子，分布平，分差小；可答 query 里也有很多"一群都相关"的，分差同样小。

### 向量 top-1 阈值扫描

阈值只用在经验类这条路上（共鸣类直接返回搜索结果、风险类不检索），所以误拒按经验层算。

| 阈值 | 无答案被拒（n = 5） | 经验层误拒（n = 23） | 共鸣层低于阈值（n = 12，仅参考） |
|---|---|---|---|
| 0.30 | 1（q074） | 1（q038） | 0 |
| 0.35 | 2（+q079） | 1 | 0 |
| 0.38 | 2 | 1 | 0 |
| **0.40** | **3（+q080）** | **2（+q002）** | 0 |
| 0.42 | 5（+q075、q077） | 2 | 1（q060） |
| 0.45 | 5 | 3（+q001） | 1 |

### 决定：0.40（`ask.refusal.min-top1-score`）

1. **train 上 0.42 更优**（5/5 全拒、误拒仍是 2），但它离可答的 q001（0.4215）只差 0.0015、离无答案的 q077（0.4167）只差 0.003——
   在 5 条负样本上把阈值卡在两个点之间的缝里，是在拟合噪声。0.40 两侧各留约 0.02。
2. **偏向少拒。** 阈值只是第一道、省钱的一道：漏过的无答案 query 还有生成层规则 3 兜底（Day 14 冒烟测试实测会答"站内没有找到相关讨论"且不带引用，
   线上把不带引用的回答也按拒答处理），代价是一次 Haiku 调用；误拒则让用户直接拿不到答案。
3. 两条误拒的 q002「脱产复习」、q038 的 **top-1 本身就是不相关帖**（第一个相关帖分别在第 9、第 3 名），送进生成层也是靠后面几条撑着。

**误拒率 2/23（8.7%），漏拒率 2/5（40%，由模型兜底）。** 样本太少，这两个数字的置信区间都很宽：
负样本只有 5 条，test 集的另 5 条留到 Day 18 一次性验证，不在这里调。

### 局限

- 阈值绑死 `voyage-4` 向量 top-1。**换 embedding 模型或检索方案（Day 17 接 rerank）必须重新校准**；rerank 是 cross-encoder 打分，
  分数可能比余弦更好用，届时一并比较（本次没有 `VOYAGE_API_KEY`，未跑 rerank 分数）。
- 5 条无答案 query 都是"X 怎么入门 / 计分"式的短句，没覆盖"站内话题相近但没人讨论过这个具体问题"这种更难的拒答。
