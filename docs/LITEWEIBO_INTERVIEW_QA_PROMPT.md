# Lite Weibo｜小红书社区内容二面与技术终面问答生成 Prompt

## 使用方法

将本文件放入 Lite Weibo 仓库根目录，向 coding agent 发送：

> 请阅读并执行 `LITEWEIBO_INTERVIEW_QA_PROMPT.md`。先检查当前仓库的实现、文档和可用的实验记录，再生成有证据支持的中文面试问答。按文件要求直接完成，缺失信息集中列出，不要停在分析计划。

以下为完整任务说明，不需要额外提供面经截图或此前聊天记录。

---

## 1. 你的角色与目标

你是一位能阅读全栈项目代码的面试教练，正在帮助项目作者准备：

**小红书 2027 校招 Product Engineer（产品工程师），社区内容方向，二面与技术终面。**

本次依据的两个面经样本都偏向项目、产品理解、个人判断与开放式讨论。按这个范围生成材料，不安排八股、算法手撕或脱离项目的框架知识问答。这些样本只用于校准提问方式，不代表所有面试的固定流程。

你的任务：

1. 理解当前 Lite Weibo 仓库真正实现了什么，以及证据能支持到什么程度。
2. 把面经中的考察意图迁移到本项目，筛选值得讨论的问题。
3. 生成可直接口述的中文回答、递进追问及回答要点。
4. 帮作者梳理选择依据、方案代价、效果证据、局限与下一步判断。
5. 明确哪些内容需要作者补充，避免替作者虚构动机、用户反馈、协作经历和成长故事。

## 2. 面经问题类型与迁移规则

下面的“二面 N”“终面 N”是原截图中的题号。已将作者个人项目的名词抽象成考察维度。

| 类型 | 来源 | 面试官关注什么 | 在 Lite Weibo 中怎样迁移 |
|---|---|---|---|
| ① 业务理解与用户价值 | 二面 1、2；终面 4 | 服务谁、解决什么问题、模块在整体中的作用 | 项目目标、核心用户任务、社交与检索问答的关系；区分学习价值与已验证的用户价值 |
| ② 个人贡献与交付过程 | 二面 3 | 独立完成范围、时间投入、交付方式 | 哪些自己做、哪些复用、如何分阶段完成；时间和贡献归属需作者确认 |
| ③ 项目演进与个人成长 | 二面 4、13；终面 1、2 | 重要节点、判断变化、兴趣与成长 | 从功能实现到质量验证有哪些变化；寻找记录佐证，不用提交历史编造心理历程 |
| ④ 技术取舍与方案差异 | 二面 12；终面 7 | 为什么这样选、替代方案、适用条件 | 混合检索、重排、推拉 Feed、固定流程与自主规划；解释代价与改变选择的条件 |
| ⑤ 评估可信度与质量定义 | 二面 5、8 | 指标是否合理、数据是否足够、人工如何参与 | 检索与回答分别如何评估、标注和划分、失败样本、指标与用户体验的关系 |
| ⑥ 反馈、时效与持续改进 | 二面 6、7、9、10 | 如何从反馈改进、避免错误累积、保持有效 | 反馈记录、数据变化、索引与缓存更新、内容失效、改进优先级；没有自动写知识库就不假定有 |
| ⑦ 结果验收与中间过程校验 | 终面 3、5 | 什么由程序检查、如何发现失败、哪里仍不确定 | 沿实际请求链检查输入、权限、检索结果、生成结果、引用、降级；讨论确定性检查的能力边界 |
| ⑧ 模糊目标的理解与拆解 | 终面 6 | 从用户目标到可验证任务，什么时候澄清 | 搜索、比较、归纳等需求如何区分；缺少约束时如何处理；未实现的交互仅作设计讨论 |
| ⑨ 模型与依赖变更 | 二面 11 | 换依赖后哪些行为可能改变、如何判断可用 | 生成模型、embedding、rerank 分别变更时的验证与回退；未迁移过不得虚构事故 |
| ⑩ 自动化边界与人的价值 | 二面 14；终面 8 | 哪些任务可自动化、谁定义目标、谁承担判断 | 社区内容任务中模型、业务代码和人的分工；讨论任务与责任，不笼统断言某岗位会被取代 |

### 必须去掉的作者专属前提

原面经涉及 Autoresearch、AI 生图、自动写知识库、热点发现、电商 Agent、实习团队中的非技术同学。**这些都不是本项目默认具有的功能或经历。**

- “生图准确率”迁移为本项目实际输出的质量定义和人工复核。
- “Autoresearch 评测集”迁移为本项目的检索或问答评测是否可信。
- “自动写知识库偏移”只迁移其数据质量与错误累积意图；若项目没有自动写入，不生成“你如何实现自动写知识库”的问题。
- “热点时效性”迁移为本项目中数据更新、过期与用户可见结果的时效要求。
- “后端作为验收者”需要结合真实链路解释，不假定代码能够保证开放式回答语义正确。
- “电商无法 Agent 化”不作为既定事实，改为具体任务的自动化条件和边界。
- “不同实习更喜欢哪段”超出单个仓库能证明的范围；在本项目中讨论个人偏好时必须由作者补充。

**可以迁移考察意图，不必保留原题措辞，也不要为了凑类型给项目添加不存在的能力。**

## 3. 项目背景：待核验的简历陈述

以下来自作者提供的简历，只是检索线索和需要核对的陈述，不能直接当作仓库已证实的事实：

- Lite Weibo 是全栈社交平台，包含账号、资料、发帖/转发、评论/点赞、关注关系、Feed 和通知。
- 使用混合推拉 Feed，对 10k+ 粉丝作者采用拉模式，并处理游标分页。
- 使用 lexical + vector 混合检索、weighted RRF 和 Voyage rerank。
- 使用 3,000 篇帖子、80 条标注查询；简历写明测试集 nDCG@10 从 0.08 到 0.85。
- 使用 Claude 实现带引用的问答，包含意图分类、阈值拒答、降级、限流和指标。
- 简历指标为引用准确率 92%、幻觉率 3.8%、拒答准确率 98%、回答帮助度 3.32/5。
- 使用 Caffeine + Redis 两级帖子缓存，以及相应的缓存保护措施。
- 点赞计数在 Redis 缓冲后幂等批量回写，采用最终一致性。
- 通知采用异步链路。

**当前代码可能已经变化。** 对不一致内容，分别注明“简历陈述”“当前代码”“历史记录/实验版本”，不要擅自选择更漂亮的数字或将多个版本拼成一套结果。

不要推定该项目已有真实用户、生产流量、团队协作或商业收益。个人学习项目可以坦诚说明其目的和验证范围。

## 4. 执行步骤

### 第一步：建立事实地图

遵守仓库已有的 `AGENTS.md` 等适用约定。先看目录与入口，再按问题定向阅读，不必逐行遍历全部文件。

重点查找：

1. README、产品或设计文档、架构说明、任务记录。
2. 用户可见的页面与交互入口，以及对应 API 和服务逻辑。
3. 社交主流程、Feed、可见性与权限、检索、问答、缓存、通知的实际调用关系。
4. 评测脚本、标注数据、数据划分、结果文件、模型与参数配置。
5. 与关键判断有关的测试、失败样本、issue 或 Git 历史（若存在）。

优先使用 `rg` / `rg --files` 定向搜索。可阅读必要的提交记录，但不要把提交日期等同于实际开发工时，把代码作者等同于完整贡献归属。

没有代码证据时，应写“在已检查范围内未找到”，并列出检查范围。区分完全未实现、存在代码但未接入、已接入但未启用、运行与上线状态未知。

### 第二步：整理证据与冲突

给关键事实分配稳定编号，如 `E01`、`E02`，注明仓库相对路径、符号/函数、必要的行号及证据类型。

证据应按问题分别解释：

- **代码**：支持实现行为和结构，不能单独证明生产表现。
- **测试**：支持被覆盖的条件下的行为，不能证明所有场景。
- **脚本**：支持计算或实验方法，存在脚本不等于已运行并得到结果。
- **结果文件**：需要与数据、配置、版本对应，才能支持具体指标。
- **文档与提交记录**：帮助理解设计或变化，也可能过期。
- **作者陈述**：支持动机、贡献、沟通和亲身经历，仍应说明与技术记录的关系。

为每个关键主张使用合适标签：

`[代码已核实]`、`[实验记录支持]`、`[仅文档陈述]`、`[存在冲突]`、`[待作者确认]`、`[改进设想]`。

推测应标为 `[推测]`，不要混入事实。若仓库提供的信息已经足够，不需要为了面试材料重新运行整套系统或付费模型评测。运行状态或环境限制导致无法确认时如实记录。

### 第三步：选择问题

默认生成 **20 道主问题**，可根据证据调整为 16–24 道，避免同义重复。其中约 10 道标为 P0，其余为 P1。

- P0：最能体现本项目的业务理解、决策质量、验证能力与反思，优先练。
- P1：补充能力边界、方案迁移或未来设计，按时间选练。
- 每题标明偏“二面”“终面”或“两者”，这是练习侧重点，不是题目预测。
- 覆盖上面的 10 类；对无法形成真实经历的问题，可用明确标注的设计讨论或待补充题，不虚构素材。
- 大部分题必须紧贴仓库真实机制和具体用户任务；开放题也要从项目出发。
- 实现细节用于支撑判断，不展开独立八股题。

### 第四步：生成回答与追问

先完成有证据的部分，剩余信息集中列在末尾。不因缺少个人动机或开发时间而停下等待。

口述回答采用自然中文，通常 180–300 字。复杂问题可以略长，但要能够在约 1–2 分钟内讲清。不要重复固定套话，不必每题机械套完整 STAR。

回答优先组织成：

**我的结论 → 一个具体场景或选择 → 依据与代价 → 实际证据 → 局限或下一步。**

使用第一人称时要守住边界：

- 已核实的实现可以写成“项目当前实现了……”。
- 缺少本人说明时，不能写“我当初发现用户……所以决定……”。
- 主观判断可以提供“候选表达，待作者确认”，供作者选择是否认可。
- 对尚未完成的改进用“如果继续做，我会……”，不能写成已采取的措施。
- 个人成长题缺少经历时，输出可填充的回答骨架与待补事实，不生成虚构的完整成长故事。

### 第五步：检查并写入文档

仅生成面试文档，不修改业务代码、配置、数据集或已有实验结果，不提交或推送 Git。

把结果写入：`docs/interview/liteweibo_community_content_qa.md`。

若该文件已有内容，先阅读并保留作者手工补充的个人经历与确认信息，再增量更新；不要直接覆盖整份已有材料。不要将本 prompt 自身或之前生成的问答当成证明项目实现的独立证据。

## 5. 必须认真分析的项目问题

以下是选题方向，并非必须照抄的题目。根据实际仓库合并、替换或删除。

### A. 价值与产品判断

- 用户要“找到一篇帖子”与“综合多篇内容得到答案”，分别需要什么体验？RAG 为哪一种任务增加价值？
- 如果这个项目最初用于学习，哪些能力已通过项目验证，哪些用户价值仍只是设想？
- 为什么把社交平台与检索问答结合？如果只有两周，你会保留什么最小闭环？
- 如果答案准确但用户不使用，先检查需求、入口、等待、信任还是其他问题？需要什么证据？

### B. 取舍、演进与改进优先级

- 混合检索、融合、重排分别对应哪些失败类型？代码可以证明这些阶段存在，实验是否证明每一步值得增加？
- 10k 粉丝阈值的实际来源是什么？无法确认时，怎样坦诚说明它目前只是设计参数？
- 如果现有问答属于固定 RAG 流程，如何解释其适用性？什么新需求才值得引入动态规划或工具选择？
- 项目当前最值得改善的一个问题是什么？用证据比较收益、成本与不确定性，不一次性列十项。

### C. 效果与评测

- 80 条查询覆盖了什么？实际开发集与测试集如何划分？是否反复用测试结果调整参数？
- 0.08 到 0.85 的基线、数据和配置是否可对应？能证明整体方案改善，还是还能区分单个模块贡献？
- 引用准确率、幻觉率、拒答准确率分别以什么为分母？与帮助度评价有何不同？
- 帮助度为 3.32/5 时，应先检查哪些失败样本？不能仅凭分数猜测根因。
- 若使用模型评分，仓库是否有评分规范与人工复核证据？哪些局限仍应承认？
- 检索指标提升而用户体验未提升，有哪些需要验证的假设？

### D. 验收、反馈与可信边界

- 沿真实链路，什么结果会被检查、拒绝、降级或返回给用户？
- 引用存在、引用指向相关文本、引用真正支持结论，分别有没有验证？不要将三者混为一谈。
- 权限、可见性、删帖、内容更新等变化，实际在哪里影响检索与回答？哪些路径尚未核实？
- 如果检索内容包含误导指令，当前边界有哪些？已实现保护与建议保护分别是什么？
- 是否记录过真实用户反馈？若没有，如何设计最小的反馈记录，让问题能够关联到原请求、候选内容和模型版本？
- 程序可以验收哪些确定性要求？对于主观“有帮助”、开放式目标或事实支持，哪些部分仍需其他评价方式？

### E. 开放目标、变化与人的作用

- 用户提出“帮我找适合我的内容”，哪些约束需要澄清？何时可以合理默认，何时必须询问？
- 模糊目标怎样转成可以检查的子任务与完成条件？结合当前项目边界回答。
- 更换生成模型、embedding、rerank 时分别需要验证什么？不要把未来迁移讨论包装成历史事故。
- 内容理解、建议生成、权限判断、实际操作和评价标准，应如何分工？
- AI 能减少哪些重复任务？用户偏好、目标定义、质量判断、责任承担如何继续影响产品设计？避免对整个职业下绝对结论。

## 6. 交付文档结构

### 第一部分：项目事实与重点概览

- 约 300 字项目概览，说明已核实范围、用户任务、当前主要限制。
- 10 类问题的覆盖表：类别、主问题编号、P0/P1。
- 关键证据表：证据编号、支持的主张、文件/符号、证据类型、限制。
- 简历与仓库的冲突或缺证清单，尤其检查各项指标。

### 第二部分：主问题、口述回答与递进追问

每道题使用下面的结构：

```markdown
### Q01｜问题标题

- 优先级：P0 / P1
- 题型与轮次侧重：……
- 面试官考察：一句话说明。
- 回答性质：已核实事实 / 候选观点待确认 / 未来设计讨论 / 待补经历。

**可口述回答**

自然中文回答；必要时明确待补信息或条件，不在口述段塞文件路径。

**递进追问**

1. 一个检验依据或替代方案的问题。
   - 回答要点：约 50–100 字，或明确尚缺什么证据。
2. 一个改变约束、检验边界或要求复盘的问题。
   - 回答要点：约 50–100 字，或说明这是设计讨论。

**证据与表达边界**

- 证据：E01、E05；必要时补充具体符号或行号。
- 待确认：只列本题关键缺口；无缺口则省略。
- 避免过度声称：本题最容易讲过头的一点；没有则省略。
```

追问要贴合本题回答，避免每题都机械重复“为什么”“怎么优化”。可以使用反例、资源减少、目标变化、模型更换、离线与体验冲突等方式。

### 第三部分：三张个人思考素材卡

从仓库中选最有证据的三个主题，建议覆盖：

1. 一次有明显代价的方案取舍。
2. 一次可以通过数据或失败案例讨论的质量改进。
3. 一次适合讨论观点变化或下一步方向的项目演进。

每张卡包含：问题与目标、实际实现、可确认的变化、候选判断、代价、证据、待作者补充。

只有代码时，写“当前方案的合理解释候选”，不能声称这就是作者当时的真实决策理由。若没有历史变化证据，第三张卡改为“待补充的复盘素材”，不要编造先失败后成功的故事。

### 第四部分：面试前速记页

- P0 问题各一句结论，指向详细题号。
- 三个最适合讲的真实机制或案例。
- 三个需要主动说明的局限。
- 五条最关键的指标/事实核对项。

### 第五部分：待作者确认

按影响排序，最多提出 6 个具体问题，优先处理会影响多个回答的缺口。例如实际项目目标、独立贡献与开发阶段、评测数据划分、是否有真实反馈、当初选择依据、最有代表性的成长事件。

不要问已经能从代码查明的事实；其他技术缺证项留在证据清单中。

## 7. 完成前自检

- [ ] 两轮面经的考察类型都已覆盖，并迁移到了 Lite Weibo。
- [ ] 没有照搬 Autoresearch、生图、电商等作者专属项目。
