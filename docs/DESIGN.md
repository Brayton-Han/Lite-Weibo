# Lite-Weibo · 语义搜索与引用问答 · 设计决策

> 本文件用 ADR（Architecture Decision Record）的格式记录 RAG 功能的关键决策：每条写**背景 → 选项 → 选择 → 理由 → 代价**。
> 数字的出处是 `docs/EVAL.md`（§ 编号指它的定稿部分，"附录 Day N"指它的过程记录）；按天的实施与排查记录见 EVAL.md 附录。
> 最后一节「已知局限」主动列出没做好、没做、或只在当前规模下成立的地方。
> 语料的来源与许可（噪声层来自 Leiden Weibo Corpus，CC BY-NC-SA 3.0，派生文本不进 git）见 EVAL §1 与 `docs/CORPUS_DESIGN.md` §5。

## 系统一览

```
                    ┌──────────── /posts/search/semantic、共鸣类"相关帖子" ────────────┐
query ──┬─ 词面路：pg_trgm word_similarity（中文）/ ts_rank_cd（英文），top-20 ─┐         │
        │                                                               ├─ 加权 RRF ─ rerank-3（前 30）─ top-k
        └─ 向量路：voyage-4 → pgvector HNSW，top-20 ────────────────────┘   (k=10, w=10)   失败退回 RRF

/posts/search/ask(/stream)：
query ─ 意图分类（Haiku 5.5）─┬─ 风险类 → 干预文案 + 热线，不检索
                              ├─ 共鸣类 → 上面那条语义搜索链，不生成
                              └─ 经验类 → 向量 top-10 ─ top-1 < 0.40 ? 拒答 : Claude 生成（API citations）
Claude 不可用 / 限流 / 熔断 → 降级：本地风险词表 → 只给检索结果
```

**约束**：语料约 3000 条帖子、单个 PostgreSQL 15、一人维护的作品集项目。下面多数决策在这个规模下成立，规模变化后需要重看的地方在各条"代价"里写明。

## ADR-1 · 向量存储：pgvector，不上独立向量库

**背景**：项目已经用 PostgreSQL 15 存帖子。语义检索每次都必须带业务过滤：帖子未删除（软删除，`@SQLDelete`）、可见性为 PUBLIC。

**选项**

| 选项 | 优点 | 缺点 |
|---|---|---|
| **pgvector（同库）** | 一条 SQL 里 JOIN `posts` 做过滤；与业务数据同事务、同备份；零新增运维 | 规模上限与 PG 绑定；HNSW 索引吃内存 |
| Milvus / Qdrant 等独立向量库 | 千万级以上性能与功能更好 | 过滤所需的业务字段要冗余一份进去，发帖、删帖、改可见性都要双写，并处理双写不一致 |
| Elasticsearch（向量 + IK 分词） | 同时解决中文分词 | 另一个有状态服务 + 同步链路；对 3000 条数据过重 |

**选择**：pgvector，HNSW 索引（`vector_cosine_ops`，`m = 16`、`ef_construction = 64`），查询时 `ef_search = 100`、开 `iterative_scan = relaxed_order`。

**理由**
- 万级数据远未到专用向量库的门槛：test 集上向量检索 p50 1.8 ms（EVAL §4）
- **过滤与检索在同一条 SQL 里**：`JOIN posts … WHERE deleted = false AND visibility = 0`，删帖、改可见性立刻生效，不存在"向量库里还有、业务库里已删"的窗口。换成独立向量库，这些都要靠双写和补偿
- HNSW 相比 IVFFlat 不需要先有数据训练聚类中心，召回-延迟曲线也更好；3000 条规模下 HNSW 的结果已与精确搜索完全相同（附录 Day 11）
- embedding 放在独立的 `post_embeddings` 表而不是 `posts` 的一列：一帖可以有多个 chunk（1:N）；换模型时新旧向量按 `model_id` 并存、可以对照；`posts` 是热表，不让 1024 维向量拖重它

**代价**
- 规划器行为要亲自盯：pgjdbc 切换到 generic plan 后，`?::vector` 每行重新解析、HNSW 被放弃，延迟 1.9 → 283 ms（已用 `SET LOCAL plan_cache_mode = force_custom_plan` 修，附录 Day 9）；
  内层 `LIMIT ≥ 150` 或 `ef_search = 200` 时规划器认为全表扫描更便宜（附录 Day 11）。**这些问题只看评测指标发现不了，要看执行计划**
- 扩到全可见性（关注者可见、仅自己可见）时，过滤会变成按用户的强过滤，HNSW 先取候选再过滤会召回塌陷（见「已知局限」）
- Hibernate 不认识 `vector` 类型，向量相关查询全部走 `JdbcTemplate` 原生 SQL

## ADR-2 · Embedding：Voyage `voyage-4`，藏在 `EmbeddingClient` 接口后面

**背景**：Anthropic 不提供 embedding 接口，必须选别家。

**选项**：Voyage AI 托管 API；bge-m3 本地部署（Python sidecar）。

**选择**：`voyage-4`，1024 维。接口 `EmbeddingClient` 把 `embedQuery` / `embedDocuments` 分成两个方法。

**理由**
- 零运维，中英双语质量好；1024 维与 bge-m3 相同，日后对照可以共用 `vector(1024)` 列
- query 与 document 的 `input_type` 编码进方法名：传错不报错、只会静默掉点，干脆不给调用方传错的机会
- 入库路径与查询路径分开处理失败：入库遇 429 按分钟级退避（Voyage 免费层 3 RPM）；查询路径快速失败，不重试 429，不让用户请求挂几分钟

**代价**
- 每次搜索多一次跨公网往返，且数据要发给第三方——所以**只向量化 PUBLIC 帖子**
- 没有做横向对比，"为什么是 voyage-4"只能答"质量与运维成本的取舍"，没有对照数据（见「已知局限」）
- 拒答阈值绑死在这个模型的余弦分数上（ADR-9）

## ADR-3 · 中文词面检索：pg_trgm，不做真分词

**背景**：原来的中文搜索是 `content LIKE '%q%'`，要求逐字包含整句 query，35 条可答 query 里有 28 条零结果（EVAL §4）。`to_tsvector('simple', …)` 按空格切词，对中文无效。

**选项**

| 选项 | 部署成本 | 质量 |
|---|---|---|
| **pg_trgm**（3 字滑窗 + GIN） | 官方镜像自带，`CREATE EXTENSION` 即可 | 近似；不理解词边界 |
| zhparser / pg_jieba | 要自建含扩展的 PG 镜像，`pgvector/pgvector` 镜像里没有；词典要维护 | 真分词，可接 `ts_rank` |
| Elasticsearch + IK | 新增有状态服务 + 数据同步 | 最好，但与 ADR-1 的"同库过滤"冲突 |

**选择**：pg_trgm。命中用 `q <% content`（走 `gin_trgm_ops`），排序用 `word_similarity(q, content)`，阈值 0.05；英文仍走 `tsvector`，排序改为 `ts_rank_cd`。

**理由**
- 部署成本最低，且与向量路同库，不破坏 ADR-1
- 用 `word_similarity` 而不是 `similarity`：后者拿短 query 和整条帖子比，偏向短帖
- 阈值 0.05 由扫参定：指标随阈值单调下降，选"不损失任何指标的最大阈值"，实际等于"至少共享一个 trigram"（附录 Day 10）
- 在当前评测集上，词面路在融合里只起 tie-breaker 作用（ADR-4），换成真分词的收益上限有限——这一条是对本评测集成立的判断，不是普遍结论

**代价**
- **不是真分词。** 短 query 没有区分度：3 字 query「小电驴」只有 4 个 trigram，48 条帖子并列 0.25，相关帖按 id 被挤出 top-10（nDCG 0.470 → 0）；
  长 query 里的常用字让候选集膨胀（最多 468 / 3157），每条都要算 `word_similarity`，是混合检索尾延迟的来源，并随语料线性增长
- pg_trgm 函数默认 `COST 1`，规划器在 custom plan 下会选 seq scan；`V5__trgm_function_cost.sql` 把成本调到 100 才全部走索引。
  对扩展成员函数的 `ALTER FUNCTION` 不会被 `pg_dump` 导出，从 dump 恢复的库要手动重跑 V5
- 正解是 zhparser / pg_jieba 或 ES + IK，没做的原因是部署成本

## ADR-4 · 融合：RRF，不用分数加权求和；最终是加权 RRF

**背景**：两路分数量纲不同——trigram 相似度 ∈ [0, 1]，`ts_rank_cd` 无上界，余弦 ∈ [−1, 1]。

**选项**
1. 分数归一化后加权求和：需要归一化参数，且分数分布随语料与 query 漂移，今天调好的权重明天就不对
2. **RRF**：只看名次，`Σ 1/(k + rank)`，不碰分数
3. 等权 RRF vs 给向量路加权

**选择**：加权 RRF，`1/(k + r_词面) + w/(k + r_向量)`，k = 10、每路 top-20、w = 10。两路在独立线程池 `searchTaskExecutor` 上并行。

**理由**
- 选 RRF 而不是加权求和，理由是量纲：RRF 只用名次，天然不受分数分布漂移影响
- **但等权 RRF 是失败的**：36 个配置全部显著输给纯向量（最好 0.635 vs 0.766）。两路 top-10 平均只重叠 1.4 条，RRF 退化成"两路前五各取一半"，
  精度只有 0.25 的词面结果被掺进来（附录 Day 11）。经典的 k = 60 在这里更差：深处的共识大多是噪声
- 给向量加权到 w = 10 后，词面独有的帖子进不了向量 top-20 之前，词面只能在两路都有的帖子之间微调顺序——对「考核期」这类专名 query 有用
- 每路 N = 20 而不是 50：N ≥ 50 不提升指标，还会让向量路内层 LIMIT ≥ 150、规划器改走全表扫描

**代价**
- **在本评测集上混合检索没有收益**：train +0.005（区间下沿 0），test −0.000，35 条里 26 条与纯向量完全相同（EVAL §4）。保留它是当作专名 query 的保险，不是主要提升来源
- w = 10 是约 100 个配置里挑出的最优点，赢家诅咒；w 变小能换来更高的 MRR（k10 w2 MRR 0.981），按 nDCG 选了 w = 10
- 多一条尾延迟随语料增长的链路（ADR-3），p50 比纯向量多约 0.6 ms

## ADR-5 · Chunk 策略：一帖一 chunk，转发拼原文

**背景**：微博是短文本。语料帖都 ≤ 200 字，库里最长 659 字，p50 77 字。

**选项**：固定长度切片；按句子切 + 重叠；一帖一 chunk。

**选择**（`PostChunker`，回填与增量向量化共用同一份规则）：
- 原创帖：正文即 chunk
- **转发并评论**：评论 + `[转发原文]` + 原帖正文。评论常常是"好烦啊"这类短句，只 embed 评论会丢掉上下文；原帖已删或非 PUBLIC 时不带原文
- **纯转发**：不生成向量。它的内容就是原帖，原帖已有向量，再来一份会让同一段文字在结果里出现两次

**理由**
- 当前数据没有一条需要切；按固定长度切短文本只会制造半句话的 chunk
- 回填与增量共用一个 `PostChunker`：两处各写一套，同一条帖子回填和新发就会产出不同的向量
- 检索 SQL 已经按 `post_id` 去重取最高分、内层多取 3 倍，为日后长帖切片留了余量

**代价**
- **长帖切片没有实现**（`chunk_index` 恒为 0）。原计划：超过阈值后按 `。！？\n` 切、相邻 chunk 重叠一句；编辑后先删全部旧 chunk 再写。真实用户发长帖时，超出模型窗口的部分会报错而不是被截断（`truncation=false`）
- 转发帖的向量依赖原帖：原帖被编辑、删除或改为非公开时，要连带重算所有转发了它的帖子（ADR-11）

## ADR-6 · Rerank：上 Voyage `rerank-3`，带降级

> 这条决定最初记在 EVAL.md「Day 12 · 决定」，此处为定稿，并补上了 test 集的结果。

**背景**：第一阶段是双塔（bi-encoder），query 与帖子各自编码，细粒度关系会丢。Day 11 之后 rrf 的 MRR 已有 0.956，空间主要在 2–10 名的顺序。

**选项**

| 选项 | 优点 | 缺点 |
|---|---|---|
| **Voyage `rerank-3`**（托管 cross-encoder） | 复用 embedding 的 key 与 REST 写法；分数可复现 | 多一次外部往返；按 token 计费 |
| 自部署 bge-reranker | 免费、数据不出网 | 1 GB+ 的模型服务要维护；TEI 镜像在 Apple Silicon 上只能模拟运行 |
| LLM listwise rerank | 灵活 | 更贵、更慢、输出不完全确定、有位置偏差，不适合放在搜索框后面 |
| 不上 | 零成本 | —— |

**决策门槛（事先定下）**：nDCG 提升 < 3% 且延迟明显增加就不上。

**选择**：上。rrf 前 30 条送 `rerank-3`，超时 2s；失败（超时、429、5xx）退回 rrf 排序，不报错，计数 `rerank.fallback`。

**理由**
- train：nDCG@10 0.771 → 0.807（+4.7%），95% 区间 [+0.005, +0.068]，35 条涨 23 条，超过门槛且显著
- 成本可以忽略：约 1,700 token / query，不到 $0.0001
- 延迟 +120 ms，对搜索框可以接受；有降级，Voyage 挂了搜索不会挂

**代价**
- **test 上没能确认显著**：+0.029，区间 [−0.003, +0.061] 跨 0（EVAL §4）。rerank 的 judged@10 只有 92.8%，被它提上来的池外帖子按不相关计分，指标偏低；
  点估计与 train 接近，方向一致。决定不推翻，但对外只能说"train 上显著，test 上方向一致但不显著"
- 搜索链路上第二次串行的外部调用（第一次是 query 向量化）
- **问答的经验类没接 rerank**：拒答阈值是按纯向量 top-1 校准的，换 rerank 分数要在 train 上重新校准（ADR-9）

## ADR-7 · 直接用官方 SDK，不用 LangChain4j / Spring AI

**背景**：生成层需要 Claude；Java 生态里有 LangChain4j、Spring AI 这类 RAG 框架。

**选项**：RAG 框架；`com.anthropic:anthropic-java` 官方 SDK + 自己写检索链。

**选择**：官方 SDK。检索链（`RetrievalStrategy` 的组合：`TsRankStrategy`、`VectorStrategy`、`HybridRrfStrategy`、`RerankStrategy`）自己写。所有 Claude 调用走唯一出口 `ClaudeGateway`。

**理由**
- **检索才是主体，而检索是自定义 SQL**：混合检索要两路并行、加权 RRF、同一条 SQL 里做业务过滤、事务内 `SET LOCAL` 控制规划器——框架通用的向量库抽象以"query → top-k 相似文档"为中心，这些都要绕开它写
- 生成层最需要控制的参数正是框架会挡住的：cache 断点放在哪、document block 上开 citations、意图分类用结构化输出（而生成层不能用，因为 citations 与 `output_config.format` 不兼容）、超时按调用分别设置
- 错误要分级处理：`ClaudeGateway` 按 SDK 的异常类区分 NotFound / RateLimit / 认证 / 上游 5xx / IO / 超时，统一转成带 `kind()` 与 `retryable()` 的 `ClaudeCallException`，降级（ADR-12）依赖这个分类
- 链路本身很薄，框架省下的代码不多

**代价**
- 流式、引用组装（`CitedAnswerAssembler`，含 code point → UTF-16 的偏移换算）、token 计量都要自己写和测
- 换模型供应商时没有现成的抽象可用

## ADR-8 · 生成层只服务经验类：意图路由 + 三路拒答

**背景**：语料按信息需求分三层（EVAL §1）。真实社交内容里只有约三成承载"有答案的问题"，其余是情绪共鸣和噪声。对"撑不下去了想裸辞"生成一段建议是产品缺陷，对有自伤倾向的 query 推一屏同样绝望的帖子是安全问题。

**选项**：所有 query 都进生成层，靠 prompt 约束；先分类再分流。

**选择**：先用 `claude-haiku-5-5` + 结构化输出把 query 分成三类：

| 意图 | 走向 |
|---|---|
| 经验类 | 检索 → 阈值拒答 → 带引用生成 |
| 共鸣类 | 不生成，直接返回语义搜索结果 |
| 风险类 | **检索之前就返回**干预文案 + 热线，既不生成也不返回任何帖子；前端在意图到达之前也不展示关键词结果 |

**理由**
- 分类调用便宜（约 880 输入 / 15 输出 token），挡在昂贵的生成调用前面，顺带省钱
- 分类 prompt 先判风险类、宁可误判不漏判；分类失败时抛异常、不猜类别，防止风险类静默落进生成层
- 结果：test 集意图准确率 40 / 40，风险留出集召回 19 / 19（EVAL §5）

**代价**
- 每次问答多一次串行的模型调用（约 2s 后意图才到达）
- 风险判断依赖模型；Claude 不可用时只能靠本地词表，召回明显下降（ADR-12）
- "夸张修辞 vs 真实风险"（"加班累死了" vs "想永远消失"、谐音"想紫砂"）的边界只有十来条标注
- 生成模型用 Haiku 而不是 Sonnet：toy 项目语料少、够用；有用性 test 上 3.32 未达标，原因主要不在模型大小（EVAL §5），但没有用 Sonnet 做过对照

## ADR-9 · 拒答判据：向量 top-1 余弦的绝对阈值 0.40

**背景**：经验类 query 检索完，要在**不调模型**的情况下判断"站内没有相关讨论"——省一次生成调用，也比让模型自己判断更可靠。Day 4 发现同一条无关文本的分数随 query 漂移（0.13 vs 0.27），当时预期要用相对判据。

**选项**（train 上逐一比较，附录 Day 14）

| 判据 | 结果 |
|---|---|
| RRF top-1 分数 | 无信号：只由名次决定，第一名几乎总是同一个值 |
| 向量 top-1 与 top-10 的分差 / 均值差 | 无信号：无答案 query 的结果"同样不相关"，分布平；可答 query 也常常"一群都相关" |
| **向量 top-1 余弦** | 唯一有区分度的 |

**选择**：向量 top-1 < 0.40 即拒答，不调模型；漏过阈值的由生成层 prompt 规则 3（"帖子不足以回答就说站内没有找到"）兜底，不带引用的回答也按拒答处理。

**理由**
- 0.42 在 train 上更好，但它离可答样本只差 0.0015、离无答案样本只差 0.003，是在拟合 5 条负样本；0.40 两侧各留约 0.02
- 偏向少拒：漏拒还有模型兜底，代价是一次 Haiku 调用；误拒则让用户直接拿不到答案
- test 上：阈值拦下 4 / 5 条无答案、误拒 0 / 22；漏过的 1 条由模型拒答，最终拒答 balanced accuracy 100%（EVAL §4、§5）

**代价**
- 绑死 `voyage-4` + 纯向量检索。换 embedding 模型、或让问答走 rerank，都要在 train 上重新校准——这正是问答没接 rerank 的原因
- 负样本只有 10 条（train 5 + test 5），且都是"X 怎么入门"式的短句，没覆盖"话题相近但没人讨论过这个具体问题"

## ADR-10 · 引用：用 API 的 citations，不让模型自己写角标

**背景**：回答里的每个结论都要能跳回原帖。

**选项**：prompt 要求模型输出 `[1][2]`；API 的 citations 机制（document block 上 `citations: {enabled: true}`）。

**选择**：API citations。每条检索结果是一个 document block，`document_index` 映射回 `postId`；`CitedAnswerAssembler` 把 text block 与引用组装成带角标的分段。

**理由**
- 模型自己写的角标本身就可能是幻觉：编号不存在、或指向不支持该结论的帖子。API 返回的 `cited_text` 是逐字截取的原文，可以机械校验
- 越界的 `document_index` 直接丢弃并告警——宁可少一个角标，也不跳到错误的帖子
- test 上引用正确率 92.4%，这是自动 judge 偏保守的上界（EVAL §5）

**代价**
- 与结构化输出（`output_config.format`）不兼容，生成层只能从 content blocks 解析
- API 的字符偏移按 code point 计，帖子里有 emoji 时与 Java / JS 的 UTF-16 下标错位，要换算
- 引用只能在生成结束后组装，所以流式阶段是纯文本，`result` 事件到达后才换成带角标的版本
- 回答被切成很多小 text block，引用只挂在最小的那一块上，给自动评判带来了误判（EVAL 附录 Day 15）

**同属生成层的安全措施**：检索到的帖子是不可信输入。system prompt 声明 document 内容都是用户数据而不是指令、问题只在 `<question>` 标签内；
`PromptLeakGuard` 在每段流式输出推给用户之前检查是否含 system prompt 的连续 12 字片段，命中即中止。实测往库里发 4 条恶意帖，它们排到了检索第 1–3 名，但 0 次劫持。

## ADR-11 · 向量生命周期：显式删除为主，读时过滤兜底，回填校正

**背景**：帖子是软删除（物理行还在），`ON DELETE CASCADE` 不触发；帖子还会被编辑、改可见性。

**选项**：只做读时过滤（检索 SQL 过滤 `deleted` / `visibility`）+ 定期清理；显式删除。

**选择**：三层都做。
- **显式**：发帖、编辑、删帖、改可见性都发 `PostEmbeddingEvent`（提交后），异步 `syncPost`：重算 chunk_text，相同则跳过，不同则重新向量化，不再需要向量则删除；并重算转发了该帖的帖子
- **读时过滤**：检索 SQL 里 `deleted = false AND visibility = 0`，加载实体后再判一次，挡住异步删除的窗口与失败残留
- **回填校正**：`EmbeddingBackfillRunner` 以数据库为准找出缺失 / 残留 / 过期三类，有只读体检模式

**理由**
- 决定性的是转发帖：它的 chunk_text 拼着原帖正文。原帖删除后，读时过滤只看转发帖自己的 `deleted`，拿原帖的话去搜仍能经由转发帖命中——只有显式重算能处理
- 内容变化时删除该帖**所有模型**的旧向量：过期比缺失更糟，缺失能被回填发现，过期不会
- 异步任务只接收 `postId`、执行时回库重读：排队期间帖子可能已被删；并发编辑用 `SELECT … FOR UPDATE` 锁住帖子行再重算

**代价**
- 独立线程池 `embeddingTaskExecutor` 队列满时丢弃任务，漏掉的帖子要靠回填补齐，而回填要人去跑；没有告警
- 发帖到可被语义搜索命中之间有一次 Voyage 往返的延迟

## ADR-12 · 降级：Claude 不可用时只给检索结果，风险判断退回本地词表

**背景**：功能的核心价值在检索，AI 回答是增强而不是依赖。但 ADR-8 规定风险类不能看到帖子，而判断风险类的正是 Claude。

**选项**
1. 意图未知时不展示任何帖子（安全，但 Claude 一挂搜索也就跟着没用了）
2. 意图未知时照常给检索结果（可用，但风险类会看到帖子）
3. **意图未知时先过本地风险词表，命中按风险类处理，否则给检索结果**

**选择**：方案 3。`AskResponse` 新增 `DEGRADED`（原因：被限流、熔断、Claude 失败或超时、线程池满）；`RiskKeywordGuard` 是纯本地关键词 + 少量正则。
配套：Redis 令牌桶限流（问答 20 次 / 小时，被限降级；语义搜索 60 次 / 分钟，被限 429）；日成本熔断（按价目表累计当日 Claude 花费，默认 5 美元）；
意图 8s、生成 30s 超时；问答结果缓存 30 分钟。

**理由**
- 实测把 `ANTHROPIC_API_KEY` 改成错的：全部 HTTP 200，普通 query 降级成语义搜索结果，风险 query 被词表拦下只给热线（EVAL 附录 Day 17）
- 限流在 Redis 不可用时放行（fail-open），熔断在 Redis 不可用时按已熔断处理（fail-closed）：前者失败的代价是多花点钱，后者失败的代价可能是失控的账单

**代价**
- **词表在风险留出集上只召回 13 / 19（68%）**，漏掉的都是委婉说法（"不想再醒来了"、"药攒够了"）。降级状态下约三分之一的风险类 query 会看到帖子而不是热线
- 这是可用性与安全之间的取舍，不是 bug。产品上若要求"降级时风险类零漏"，应改回方案 1
- 没有对着漏掉的 6 条补词——那样留出集就变成了开发集；改进词表要先另写一份留出集
- 熔断是软上限，在途请求会略微超出

## ADR-13 · 评测先行，test 集各只跑一次

**背景**：所有"优化"如果没有尺子，都只是感觉。

**选择**：先建评测集再调参。80 条 query，pooling 构造候选池（4 个检索系统各取 top-20 + 种子帖所在的同义表达族），train / test 各 40；调参只在 train 上做，test 只跑一次（EVAL §2）。
生成层自动评判用 `claude-haiku-4-5`，与生成模型不同，避免自己评自己；指标口径在看到任何生成层数字之前定下。

**理由**：只标注某一个系统的输出，评测就成了自我验证；在 test 上调过参，test 就失去意义。

**代价**：评测集小、语料是合成的，绝对值不能外推（见「已知局限」）；为了不污染 test，有些 test 上暴露的问题（有用性不达标、问答没接 rerank）只能记下，不能回头用 test 调。

## 已知局限

### 检索

1. **trigram 不是真分词。** 短 query 没有区分度（「小电驴」并列 48 条），长 query 候选集膨胀、尾延迟随语料增长。正解是 zhparser / pg_jieba 或 ES + IK，没做是因为部署成本（ADR-3）
2. **只检索 PUBLIC 帖；扩展到全可见性时会遇到 ANN 过滤下的召回塌陷。** 现在只向量化 PUBLIC 帖子，过滤条件几乎不会删掉候选。
   一旦要按"当前用户能看到什么"过滤（关注者可见、仅自己可见），对多数用户来说大部分向量都不可见：HNSW 先按 `ef_search` 取一批候选再过滤，剩下的可能远不足 k 条。
   `iterative_scan` 能继续往下扫，但代价随过滤选择性变差而上升。可能的方向是按可见性分区建索引，或先按可见集合预过滤再做精确距离计算
3. **长帖切片没有实现**，`chunk_index` 恒为 0（ADR-5）
4. **混合检索在本评测集上没有收益**，rerank 的收益在 test 上不显著（ADR-4、ADR-6）
5. **问答的经验类仍走纯向量 top-10**，没有接 RRF 与 rerank，因为拒答阈值要重新校准（ADR-9）
6. **英文路没有评测样本**：80 条 query 全部含汉字，`ts_rank_cd` 的改动未被量化
7. **只在 3000 条规模上测过。** `ef_search` 测不出质量差异、HNSW 与精确搜索结果相同；trgm 候选集与全表扫描成本都随语料线性增长，上量后要重测。没有做过并发压测

### 评测

8. **评测集只有 80 条，统计置信度有限**：每个 query 类型 5–13 条，单条 query 能让组均值动 0.1 左右；无答案只有 10 条
9. **语料是按语义簇合成的**：相关帖平均 85% 来自种子帖所在的族，恰好是 embedding 最擅长的形态。策略间的方向可信，绝对值与幅度不能外推（EVAL §8）
10. **embedding 模型未做横向对比**：只用了 `voyage-4`，没有跑 bge-m3 对照
11. **标注几乎全来自 Claude**：5,148 个检索判定中只有 100 对以人工为准；生成层评判的校准标注者是 Claude Opus 5.5，不是人；校准样本里没有一条错引用，没有证明评判能抓出错引用

### 生成与安全

12. **答案有用性 test 上 3.32，未达标**（目标 3.5）。"站内没有找到明确结论"的拒答句混进正常回答、前后矛盾，这个问题至今没修
13. **降级时风险词表召回 68%**（ADR-12）
14. **风险边界标注少**：夸张修辞、谐音黑话只有十来条标注；"朋友说想自杀怎么劝"这类第三人称提问该走哪一路是产品决定，还没有定

### 运维

15. **向量化任务队列满时丢弃，靠人工跑回填补齐**，没有告警（ADR-11）
16. **`V5__trgm_function_cost.sql` 不会被 `pg_dump` 导出**，从 dump 恢复的库要手动重跑（ADR-3）
17. **限流按用户，不按 IP**；Redis 不可用时限流放行
